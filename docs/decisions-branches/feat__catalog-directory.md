## 2026-08-18 01:30 - The catalog's directory becomes a generated, gated skill so it travels to subscribers

**Reasoning:** #229: the README table names all 49 skills and stays in this repo. A subscriber installs into .claude/skills/ and gets N directory names and no map, so an agent concludes coverage is absent and rewrites guidance that already exists -- twice this week. A skill is the only artifact that travels, so the directory is one: skills/finding-a-catalog-skill, rendered by .github/scripts/gen_skill_directory.py from docs/placement-map.json, and re-rendered in process by validate_skills on every PR so a committed body that differs fails. Source is the placement map rather than frontmatter because the map is ALREADY reconciled 1:1 against skills/, so requiring the two new keys (family, owns) there makes a skill impossible to add without a directory line -- and because nine skills are repo-mirrored, where a required frontmatter key would redden a foreign release-sync PR the mirror never agreed to. Format is family routing line + one <=32-byte ownership fragment per skill: measured 6212 bytes at n=50, ceiling 75 inside the reserve and 80 at the 8192 cap exactly.

**Alternatives considered:** Reuse the README purpose column (rejected: sums to 8515 bytes over 49 skills -- over the whole body cap before a single name or bullet, and it is the hand-kept artifact #229 exists to eliminate), Generate from frontmatter description (rejected: 27363 bytes, 3.3x the cap, and it is a trigger surface -- 'Use when about to...' -- not a statement of what a skill owns), Route by frontmatter kind (rejected: present on 5 of 49, three legal values, and none of them separates orchestration from colour primitives), Bare names under each family, no per-skill text (rejected on value, not bytes: it renders 4575 bytes at n=50 and reaches ~150 skills, but an agent seeing 'visual-polish' and 'token-frugal-tooling' as bare names still cannot tell whether either covers what it is about to write -- which is the whole question #229 is about. 25 skills of headroom is the price of the column that does the work), Split the directory in two when it outgrows the cap (refused, and the refusal is written into size_error(): a map you must know to look in two places for is not a map, and a subscriber installing one half gets one that lies by omission -- #229's failure exactly), Put summary/family in a new docs/skill-directory.json (rejected: two lists to keep 1:1 against skills/ is two chances to diverge; one registry, gated once)

**Implications:**
- docs/placement-map.json gains a top-level ordered families array and two REQUIRED per-skill keys. Adding a skill now needs both, and the gate says so on the PR that adds it
- The directory ceiling is 75 skills, stated not discovered. gen_skill_directory.size_error() refuses past a 7900-byte reserve and names four ladder rungs, each with the value measured when the format was chosen; the last rung is retirement, which curating-a-skill-catalog already owns
- The 'deliberately not here' section is measured at generation time against skills/, with a control probe that MUST match -- so a gap that gets filled refuses to render rather than going on advertising itself, and an uncontrolled zero cannot ship
- Eight census-visible consumer repos are declared as subscribers and none subscribes yet, so the weekly placement cross-check will file a missing verdict until each runs npx skills add. thrillmade/arlyn-working -- the repo #229 measured -- is deliberately NOT declared: it is absent from census_counters.CONSUMER_REPOS, so a declaration there could never clear
- Still open from #229: the per-skill footer linking up to the directory. Measured, a 65-byte footer breaks 8 of 49 skills at the cap (test-discipline has 1 byte of headroom) and each trim needs a docs/prose-removals.md row, so it is its own item. And the README table remains a second hand-kept owner of the same fact
