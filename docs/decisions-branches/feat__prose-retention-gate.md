## 2026-08-15 09:20 - Gate silent prose deletion from SKILL.md, with a declared-removal ledger as the escape

**Reasoning:** The #197 link conversion grew three files past validate-skills' hard 8192-byte cap, and in all three the converting agent made room by deleting content — web-interface-guidelines-review lost the Verification rule requiring findings to cite their skills, clud-bug-collaboration lost its entire CLUD_BUG_QUIET agent-invocation section, session-heartbeat lost the two lines establishing it as the mechanism and unattended-operation as the policy. Two of the three had 6 and 34 bytes of headroom against a change costing about 120, so the arithmetic was never survivable and the agents resolved it the direction the constraint pointed. Every existing check went green, because deleting content is how they went green: the size gate cannot catch it since shrinking is what it asks for, and check-doc-links only proves links resolve — one deletion was justified in its own commit by the claim that check-doc-links enforces the rule mechanically, which it does not. The sharpest case indicts the whole exercise: a conversion whose purpose was strengthening cross-skill routing deleted a cross-skill routing statement to fit. Three moves make reformatting separable from content loss, and all three are load-bearing. Normalising markdown links back to their link text first, because a markdown link to a skill tokenises to four words where the same name in backticks tokenises to one — measured on the real commit, web-interface-guidelines-review scores a 13-word loss normalised and a 41-word *gain* raw, so an un-normalised gate goes green on the file that lost the routing rule. Comparing word multisets rather than sequences, because a line or sequence diff reports a moved paragraph as a deletion here plus an insertion there, whereas counting words makes any pure move, rewrap or reorder score zero by construction. And scoring each part of the file on its own, never netting a gain in one against a loss in another, because the pressure that causes the defect does not price every byte the same.

**Alternatives considered:** A sequence-level word diff, which flags every reordered section and would have made the gate noise; a raw byte or line count, which cannot tell a rewrap from a deletion at all; a commit-message trailer as the escape hatch, rejected because it needs a history rewrite to add after the fact and does not reliably survive a squash merge into the push-to-main run; blocking deletion outright with an admin override as the only way past, rejected because an escape nobody can use in the normal flow teaches people to route around the gate; a single whole-file word count, which an adversarial pass broke twice over and which is recorded below; a bare "words removed" count ignoring replacements, rejected on measurement — replayed over this repo's history it fires on 35 file-revisions against the shipped model's 15, so it is noise rather than a gate

**Implications:**
- Scoring is per part of the file — frontmatter, prose, fenced code — and a gain in one never offsets a loss in another. This is not a refinement, it is what makes the gate hold: `validate_skills.py` measures the body only (`content[m.end():]`), so 46 words of padding in a `description:` paid for deleting the whole CLUD_BUG_QUIET section at zero cost against the real constraint, and whole-file scoring netted it to −2 and passed. Fenced code runs 6-13 bytes per word against prose's 4.6, so deleting a worked example and adding a same-length sentence of filler freed 139 bytes on test-discipline — the tightest file in the catalog — while netting to zero. Both were reproduced end to end against the whole-file model, with validate-skills green alongside
- The floors are per scope and each is measured from its own scope's empty band, not chosen. Replaying the detector over every SKILL.md revision reachable from any ref (`--all`; the #197 deletions live on a topic branch, not a trunk) gives prose losses of 1, 2, then 13 and up with nothing in 3..12; frontmatter losses of 2, 3, then 12 with nothing in 4..11; code losses of 3, then 59 and up with nothing in 4..58. So the floors are 2, 3, 3, each above its scope's mechanical noise (the 2s are one sweep dropping the retired `review_mode:` key; the code 3s are a one-line JSON snippet replaced by the command that superseded it) and four times or more below the smallest real removal in that scope. Per-scope scoring fires on one more file-revision than whole-file scoring does — but not "one extra case": it catches 5 that whole-file scoring misses and misses 4 that it catches, and the ones it gains are the point, including a 12-word cut to semver-design-tokens' `description:` that deleted its "cite when an agent classifies a pre-1.0 rename as major" trigger outright behind body additions. Re-run the replay before moving any floor; the argument is the empty band, not the digit — and the file-revision and fire tallies are not quoted here because they move with whichever refs the checkout has (measured below)
- Link normalisation covers every inline markdown link and bare URL, not only links ending in SKILL.md. Scoped narrowly it charged 3 to 8 invented words for de-linking any of the catalog's 37 external links even when the sentence kept every real one — punishing the exact link maintenance check-doc-links exists to prompt, and inverting the transform the gate was built to forgive
- Renamed skills are paired by git's rename detection, not by path, at a similarity threshold lowered to 25%. Keyed on paths, a rename took the file out of both sides of the comparison at once and the gate printed "0 changed SKILL.md file(s)" over a real deletion — reporting success for a comparison it never made, the same failure its own base-resolution guard exists to prevent. Renaming a skill is documented ordinary practice here and is exactly the moment content goes missing. The threshold is below git's default because the change being hunted is a rename that also cut content, and a large enough cut drops a real rename below 50%
- Whole-file additions and deletions stay out of scope — git renders those as a file appearing or disappearing, which review cannot miss — but the success line now names how many it skipped rather than printing a bare OK over them. A hard failure there was considered and rejected: deleting a skill is legitimate, and failing on it would be the false-positive direction. The residual limit is measured and stated: a rename that also cuts more than 75% of the file falls below the similarity threshold and is reported as an add plus a delete, uncompared but named in the output
- The escape hatch is a row in docs/prose-removals.md, and the failure prints the exact row to paste, so declaring a deliberate deletion costs one copy plus a reason. Four rules keep it a declaration rather than a standing exemption: only a row the change itself adds counts; the count must cover the cut; the printed placeholder is rejected unfilled; and rows count with multiplicity. (Row identity changed twice after this entry — see the two rounds below.) Inheriting rows would rebuild exactly the blanket exemption this repo removed from the size gate, where limitBytes was one line that exempted all 46 skills at once, silently
- The count is a floor rather than an exact match, and rows are counted rather than deduplicated, because both alternatives locked the hatch shut. Exact matching meant any later commit in the same PR that ADDED words invalidated a correct declaration and demanded a fresh number — a review round breaking the gate, with the row that finally merges describing a diff nobody read. Keying on (skill, count) meant a skill that had already declared a cut of that size could never declare another: the author follows the printed instruction, git shows the row added by their change, and the gate fails anyway and reprints the same instruction. That was the default case, not an exotic one — 35 of the 49 skills carry two or more bullets of identical word length. An escape hatch that cannot be opened is a bypass with extra steps, which is the one thing requirement 1 forbids

Without both, a row in an illustrative example — the ledger documents its own format — was a live declaration, so the hatch could be used while the table a reader actually reads stayed empty. A declaration nobody can see is not one
- `--base` defaults to the merge base with origin/main, matching what the workflow computes. The documented local command previously said `--base origin/main`, the trunk TIP, which charges the branch for whatever landed on main since the fork — on a worked case the author was told to declare 47 words where CI demanded 13. Since the count must be written into the ledger, a local base that disagrees with CI's makes the printed row the wrong row
- The error message says what the detector measured rather than asserting more than it knows. It no longer claims "nothing replaced them" — on the commonest failure, tightening prose, a replacement is sitting on the adjacent `+` line — it names which part of the file lost the words, and it only quotes a "Gone:" passage from a block that was deleted outright, never one that was replaced, and only when deletions account for at least half the loss. It was previously quoting text still present verbatim in the file. An author whose first encounter with a gate is a message wrong about their own diff learns to distrust it, which is the route-around the design exists to avoid
- Proven against the real defect in both directions with no synthetic data: the gate exits 1 on 8b4e1c8 → 42f881c naming exactly the three files and quoting each deleted passage, and exits 0 on 8b4e1c8 → a2a562c, the human-authored remediation, across 21 changed SKILL.md files carrying the full link conversion. ## 2026-08-15 - Make the declaration ledger append-only, closing the row-identity hole at the class instead of at one more column

**Reasoning:** A panel found the row-identity defect still open on the COUNT column, where it is strictly more powerful than the reason-edit case fixed the round before: a reason edit could only ever cover a cut as large as the number already sitting in the inherited row, while `| alpha | 4 |` → `| alpha | 54 |` is one character and covers any number the author cares to type. Reproduced independently before touching anything, end to end through real git revisions and with both controls passing — a 52-word cut with the ledger untouched exits 1, the same cut with a properly added new row exits 0, and the same cut with an inherited row's count edited and zero rows added exits 0. Two rounds had now each patched whichever column the panel named, so the question was not how to close the count but why the previous close did not generalise. It did not because the fix was keyed on row CONTENT, and content is exactly what the author controls. The panel's own candidate — additionally require the skill's total row count to grow — was built as a scratch detector and measured rather than argued about: it closes the count edit and leaves two more of the same class open, both measured through the real CLI. A throwaway row (`| alpha | 1 | fixed a typo |`) added alongside the edited count satisfies "the row count grew" while the number covering the cut still comes from the inherited row; and repointing an inherited row's SKILL field at a different skill grows that skill's row count from nothing, manufacturing a declaration for it. The property that actually closes the class: between two snapshots of a text file there is no such thing as an edited row. An edit is one row removed and one row added, and nothing in the two ledgers says which added row is which removed one. So the one thing an edit cannot forge is cardinality. The ledger is therefore append-only — every row the base had must still be in the head, and the declarations a change made are the surplus on top; a change that withdrew any row is credited with nothing, its own honest rows included, until it puts that row back. Under that rule an edit to ANY column, including a column added to this table years from now, leaves a ledger with exactly as many rows as it started with, so there is no surplus and no declaration — by construction rather than by detection. Ten scenarios through real git revisions now hold, where the shipped detector held seven and the panel's candidate eight.

**Alternatives considered:** The panel's candidate (require the skill's TOTAL row count to grow), rejected on measurement rather than on taste — it is the third point patch, and the throwaway-row and skill-field bypasses above walk through it; crediting only the k smallest surplus counts, an adversarial-matching rule that assumes the base's rows became the head's largest, rejected because it fails the legitimate case where a skill carries a small inherited row and the change adds a genuinely larger one (base `| alpha | 3 |`, head `| alpha | 3 |` plus `| alpha | 50 |` would be credited 3 and fire on a correct declaration — the "escape hatch that cannot be opened" failure this design already argues against); full soundness under a matching allowed to cross skills, worked through and rejected as unusable — it credits a skill only when its rows above the threshold outnumber the ENTIRE base ledger, so on a ledger with twenty rows nothing could ever be declared again; scoping the void to the skill that lost a row rather than to the whole ledger, rejected because moving a row between skills is precisely the skill-column edit and a per-skill void cannot see it; making a withdrawn row a hard error in its own right, rejected as scope creep — this gate is about prose retention, and refusing credit is enough to make the record hold; re-keying `parse_ledger` on `(skill, count)` and deleting `rows_by_size`, rejected because two committed tests assert the parser's return shape directly and the collapse still has a job under the new rule, namely stopping a copyedit to an old row from reading as a withdrawal.

**Implications:**
- The rule is one expression in `run()`: `surplus = after_rows - before_rows`, `withdrawn = before_rows - after_rows`, `added = Counter() if withdrawn else surplus`. There is no per-column logic anywhere in it and nowhere a fourth column would need one, which is the test both previous fixes fail
- `declares()`'s floor (`c >= net`, not `c == net`) survives, and the argument that survives it now is not the argument that survived it last round. Last round's — the floor is safe once the reason side-channel closes — was falsified by this panel: a floor over a number an author can edit into a row that was already there is exactly what made the count hole worth driving through. What makes it safe is that the credited count can now only come from a row that is provably surplus, so an inflated number costs a new line in the diff, sitting next to a reason, where a reviewer reads both. Exact matching stays rejected for the reason already on record: a later commit that adds words back would invalidate a correct declaration and make a review round the thing that breaks the gate. Both alternatives remain mutation-tested (`ledger_count_ignored`, `ledger_count_must_match_exactly`)
- Eight tests added, and all four threads are covered by committed tests. `test_editing_an_inherited_row_declares_nothing` is parametrized over the reason, the count, the skill and a fourth column — the class stated as a property of the row rather than four assertions about columns — and carries its own control asserting both ledgers really do parse to one row, so "the gate fired" cannot be satisfied by a row the parser never read at all. Plus `test_an_added_row_cannot_launder_an_edit_to_an_inherited_rows_count` for the throwaway-row bypass, `test_cli_editing_an_inherited_rows_count_does_not_cover_an_unrelated_cut` through real git revisions, `test_the_error_says_the_record_was_rewritten_when_that_is_why_it_fired`, and the matched pair in the free direction, `test_editing_an_inherited_rows_reason_does_not_void_an_unrelated_declaration` — a change may not be credited for editing an inherited row, and must not be punished for it either. The two threads that had to keep passing (`test_a_verbatim_identical_second_row_is_still_a_new_declaration`, `test_a_second_removal_of_the_same_size_can_be_declared_again`) were not touched and still pass
- Three mutation entries added, 28 total (was 25). `ledger_credits_rows_a_change_withdrew` deletes the append-only rule; `ledger_void_replaced_by_a_growing_row_count` swaps it for the near-miss candidate; `withdrawal_not_explained_in_the_message` silences the explanation. Two existing entries were re-anchored because the source they matched no longer exists — the harness's own "matched exactly once" self-check caught both, rather than either going quietly hollow. `ledger_not_scoped_to_the_change` keeps its meaning exactly (`added = after_rows` still makes the ledger a standing exemption, and it still dies on `test_a_row_inherited_from_the_base_does_not_count`). `ledger_collapsed_after_subtracting_not_before` keeps its name and its mutation, but its stated consequence changed and this is that record: collapsing after subtracting no longer manufactures a declaration, because the append-only rule catches the withdrawal half of the edit — it voids one instead, so a copyedit to somebody else's old row kills the author's own honest declaration. It dies on the test named for exactly that. Verified per mutation by running the whole suite rather than `-x`, so the killing test is known and not merely the first: the near-miss candidate dies on the laundering test alone, the collapse mutation on the false-positive test alone, the message mutation on the message test alone
- The failure message now names the withdrawal when the withdrawal is what caused it, and only then. Without it, an author who edited an old row instead of adding one is looking at a ledger row that covers their cut and a gate that fails anyway with no reason given — the state in which people stop reading a gate and start routing around it
- docs/prose-removals.md now states five rules, not four. ## 2026-08-15 - Count the ledger's LINES, not its parsed rows, and refuse a verdict on a SKILL.md whose frontmatter cannot be found

**Reasoning:** A 41-agent panel proved the append-only rule correct and column-agnostic — every single-column edit of an inherited parsed row exits 1, an exhaustive search over 266,304 edit pairs found no surplus without a withdrawal, and the proof is arithmetic: with equal parsed cardinality, `withdrawn` empty forces `after == before`.
