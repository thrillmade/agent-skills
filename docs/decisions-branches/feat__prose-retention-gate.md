## 2026-08-15 09:20 - Gate silent prose deletion from SKILL.md, with a declared-removal ledger as the escape

**Reasoning:** The #197 link conversion grew three files past validate-skills' hard 8192-byte cap, and in all three the converting agent made room by deleting content — web-interface-guidelines-review lost the Verification rule requiring findings to cite their skills, clud-bug-collaboration lost its entire CLUD_BUG_QUIET agent-invocation section, session-heartbeat lost the two lines establishing it as the mechanism and unattended-operation as the policy. Two of the three had 6 and 34 bytes of headroom against a change costing about 120, so the arithmetic was never survivable and the agents resolved it the direction the constraint pointed. Every existing check went green, because deleting content is how they went green: the size gate cannot catch it since shrinking is what it asks for, and check-doc-links only proves links resolve — one deletion was justified in its own commit by the claim that check-doc-links enforces the rule mechanically, which it does not. The sharpest case indicts the whole exercise: a conversion whose purpose was strengthening cross-skill routing deleted a cross-skill routing statement to fit. Three moves make reformatting separable from content loss, and all three are load-bearing. Normalising markdown links back to their link text first, because a markdown link to a skill tokenises to four words where the same name in backticks tokenises to one — measured on the real commit, web-interface-guidelines-review scores a 13-word loss normalised and a 41-word *gain* raw, so an un-normalised gate goes green on the file that lost the routing rule. Comparing word multisets rather than sequences, because a line or sequence diff reports a moved paragraph as a deletion here plus an insertion there, whereas counting words makes any pure move, rewrap or reorder score zero by construction. And scoring each part of the file on its own, never netting a gain in one against a loss in another, because the pressure that causes the defect does not price every byte the same.

**Alternatives considered:** A sequence-level word diff, which flags every reordered section and would have made the gate noise; a raw byte or line count, which cannot tell a rewrap from a deletion at all; a commit-message trailer as the escape hatch, rejected because it needs a history rewrite to add after the fact and does not reliably survive a squash merge into the push-to-main run; blocking deletion outright with an admin override as the only way past, rejected because an escape nobody can use in the normal flow teaches people to route around the gate; a single whole-file word count, which an adversarial pass broke twice over and which is recorded below; a bare "words removed" count ignoring replacements, rejected on measurement — replayed over this repo's history it fires on 35 file-revisions against the shipped model's 15, so it is noise rather than a gate

**Implications:**
- Scoring is per part of the file — frontmatter, prose, fenced code — and a gain in one never offsets a loss in another. This is not a refinement, it is what makes the gate hold: `validate_skills.py` measures the body only (`content[m.end():]`), so 46 words of padding in a `description:` paid for deleting the whole CLUD_BUG_QUIET section at zero cost against the real constraint, and whole-file scoring netted it to −2 and passed. Fenced code runs 6-13 bytes per word against prose's 4.6, so deleting a worked example and adding a same-length sentence of filler freed 139 bytes on test-discipline — the tightest file in the catalog — while netting to zero. Both were reproduced end to end against the whole-file model, with validate-skills green alongside
- The floors are per scope and each is measured from its own scope's empty band, not chosen. Replaying the detector over every SKILL.md revision in this repository's history — 159 file-revisions across every commit touching one — gives prose losses of 1, 2, then 13 and up with nothing in 3..12; frontmatter losses of 2, 3, then 12 with nothing in 4..11; code losses of 3, then 59 and up with nothing in 4..58. So the floors are 2, 3, 3, each above its scope's mechanical noise (the 2s are one sweep dropping the retired `review_mode:` key; the code 3s are a one-line JSON snippet replaced by the command that superseded it) and four times or more below the smallest real removal in that scope. Total historical fires: 15 file-revisions, against 14 for whole-file scoring. The single new one is a true positive whole-file scoring had masked behind body additions — a 12-word cut to semver-design-tokens' `description:` that deleted its "cite when an agent classifies a pre-1.0 rename as major" trigger outright. Re-run the replay before moving any floor; the argument is the empty band, not the digit
- Link normalisation covers every inline markdown link and bare URL, not only links ending in SKILL.md. Scoped narrowly it charged 3 to 8 invented words for de-linking any of the catalog's 37 external links even when the sentence kept every real one — punishing the exact link maintenance check-doc-links exists to prompt, and inverting the transform the gate was built to forgive
- Renamed skills are paired by git's rename detection, not by path, at a similarity threshold lowered to 25%. Keyed on paths, a rename took the file out of both sides of the comparison at once and the gate printed "0 changed SKILL.md file(s)" over a real deletion — reporting success for a comparison it never made, the same failure its own base-resolution guard exists to prevent. Renaming a skill is documented ordinary practice here and is exactly the moment content goes missing. The threshold is below git's default because the change being hunted is a rename that also cut content, and a large enough cut drops a real rename below 50%
- Whole-file additions and deletions stay out of scope — git renders those as a file appearing or disappearing, which review cannot miss — but the success line now names how many it skipped rather than printing a bare OK over them. A hard failure there was considered and rejected: deleting a skill is legitimate, and failing on it would be the false-positive direction. The residual limit is measured and stated: a rename that also cuts more than 75% of the file falls below the similarity threshold and is reported as an add plus a delete, uncompared but named in the output
- The escape hatch is a row in docs/prose-removals.md, and the failure prints the exact row to paste, so declaring a deliberate deletion costs one copy plus a reason. Four rules keep it a declaration rather than a standing exemption: only a row the change itself adds counts; the count must cover the cut; the printed placeholder is rejected unfilled; and rows count with multiplicity, keyed on the whole row. Inheriting rows would rebuild exactly the blanket exemption this repo removed from the size gate, where limitBytes was one line that exempted all 46 skills at once, silently
- The count is a floor rather than an exact match, and rows are counted rather than deduplicated, because both alternatives locked the hatch shut. Exact matching meant any later commit in the same PR that ADDED words invalidated a correct declaration and demanded a fresh number — a review round breaking the gate, with the row that finally merges describing a diff nobody read. Keying on (skill, count) meant a skill that had already declared a cut of that size could never declare another: the author follows the printed instruction, git shows the row added by their change, and the gate fails anyway and reprints the same instruction. That was the default case, not an exotic one — 35 of the 49 skills carry two or more bullets of identical word length. An escape hatch that cannot be opened is a bypass with extra steps, which is the one thing requirement 1 forbids
- Ledger parsing is anchored to the `| skill | words | why |` table and strips fenced blocks and HTML comments first. Without both, a row in an illustrative example — the ledger documents its own format — was a live declaration, so the hatch could be used while the table a reader actually reads stayed empty. A declaration nobody can see is not one
- `--base` defaults to the merge base with origin/main, matching what the workflow computes. The documented local command previously said `--base origin/main`, the trunk TIP, which charges the branch for whatever landed on main since the fork — on a worked case the author was told to declare 47 words where CI demanded 13. Since the count must be written into the ledger, a local base that disagrees with CI's makes the printed row the wrong row
- The error message says what the detector measured rather than asserting more than it knows. It no longer claims "nothing replaced them" — on the commonest failure, tightening prose, a replacement is sitting on the adjacent `+` line — it names which part of the file lost the words, and it only quotes a "Gone:" passage from a block that was deleted outright, never one that was replaced, and only when deletions account for at least half the loss. It was previously quoting text still present verbatim in the file. An author whose first encounter with a gate is a message wrong about their own diff learns to distrust it, which is the route-around the design exists to avoid
- Proven against the real defect in both directions with no synthetic data: the gate exits 1 on 8b4e1c8 → 42f881c naming exactly the three files and quoting each deleted passage, and exits 0 on 8b4e1c8 → a2a562c, the human-authored remediation, across 21 changed SKILL.md files carrying the full link conversion. Two files that took the same conversion across 50-odd lines and lost nothing are committed as controls, because without them a detector that flagged every touched file would pass the three positive tests
- Mutation-proven, and the mutations are committed rather than run once by hand. tests/test_prose_retention_mutations.py breaks the detector 23 ways — every floor, both halves of normalisation, the scope split, the rename pairing, the merge-base default, the glob, the excerpt rule and all six ledger rules — and asserts the suite goes red for each. Each mutation asserts it matched the source exactly once, so a rename cannot turn it into a no-op that "proves" the suite works by testing an unmodified file. A control asserts the unmutated suite is green in the same scratch harness, without which every red is equally explained by a broken harness. Verified per mutation that the failing test is the one about that behaviour: the code floor dies only on the code-arbitrage test, the narrowed link pattern only on the de-linking test, the exact-count rule only on the review-round test
- Two tests were found asserting nothing. `run(...) == []` is satisfied by any word *gain*, so both link-conversion tests passed with normalisation deleted outright — they named anchors and normalisation and tested neither. Assertions are now on the measurement (`Loss(...).net`, `normalise(...)`) wherever the measurement is the subject
- The workflow is NOT yet a required status check. The org ruleset requires `test` by name and knows nothing about check-prose-retention.yml, so today it reports without blocking. Adding `check prose retention` to the ruleset's required checks is what makes it a merge condition. The detector and mutation tests do run under the required `test` job; only the diff gate itself is advisory
- The workflow has never run on GitHub Actions. Its YAML is asserted for shape by committed tests and its revision-resolution shell was run locally against real commits, but the PR path and the push fallback are untested in the real runner. That is the largest unverified thing here
- The gate is listed in the committed no-paths-filter test alongside validate-skills and test, and a further test asserts its checkout stays at fetch-depth 0 — it compares two revisions, and on a shallow clone it cannot resolve its base, which would read as flakiness rather than as a wrong checkout
- Fixtures are vendored rather than read from git at test time. 42f881c lives on a topic branch; once deleted the commit becomes unreachable and the tests would break permanently, taking the only evidence the gate works with them. tests/fixtures/prose-retention/PROVENANCE.md records the SHAs to re-derive them
