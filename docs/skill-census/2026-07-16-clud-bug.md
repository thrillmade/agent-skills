## §6 Sync readiness

**Conditional.** clud-bug can be a live *subscriber* — but its **published-upstream skills must never be a subscribe target.**

- **Would accept weekly refresh PRs** for *subscribed* skills into `.claude/skills/` — cleanly, since strict-mode review gates them.
- **Hard guardrail (biggest breakage risk):** an auto-refresh that writes to `templates/skills/**` would silently mutate the **shipped npm bundle** every clud-bug install receives — a product release, not a cron. Publish-mode skills flow *out* (nomination PRs); the reservoir + product bundle are downstream mirrors of clud-bug's authoring copy, which is the source of truth.
- **Would subscribe (new, don't today):** `orchestrating-elite-agent-qa`, and a `technical-writing` skill once it exists.
- **Immediate cleanups the census surfaces:** register the untracked `clud-bug-brand-voice`; reconcile the drifted `clud-bug-collaboration` copy.

## §7 Additional context (interop + placement — bonus)

- **clud-bug is itself a distribution RAIL, not just a repo in the census.** Your model lists "clud-bug's pinned-ref fetch" as a *subscribe* mechanism — that fetch, the `.clud-bug.json` manifest, and base-ref skill loading are clud-bug's, and they're how skills reach every clud-bug-installed repo (hosted bot + local max mode). So editorial decisions about clud-bug's *own* skills, and any change to its loader, ripple to all subscribers. Treat clud-bug as both a census subject and shared infrastructure.
- **Frontmatter interop schema (align the reservoir's `validate-skills.yml` to this).** clud-bug's `parseFrontmatter` recognizes: `name`, `description`, `source`, `review_mode` (`shared` | `dedicated`), `kind` (`design` | review/context), `voice_scope`, and `applies_to` (`{paths, extensions, author}` globs). A skill promoted to the reservoir that uses fields clud-bug doesn't parse will silently lose that behavior when loaded via clud-bug — so the catalog validator should stay a **compatible superset** of this schema, and design skills need `kind: design` + `review_mode: dedicated` to route to the visual critic.
- **Default-on vs opt-in matters for placement.** The 4 **baseline** skills auto-install on *every* `clud-bug init` (default-on, org-wide reach); the 4 **design** skills are opt-in (`clud-bug init --with-design`). The placement map should tag which promoted skills become default-on — they have the widest blast radius.
- **A three-copy drift the reservoir should collapse.** The same baseline skills exist in ≥3 places across 2 repos, already drifting: `clud-bug/templates/skills/baseline/` (the shipped source), `clud-bug/.claude/skills/` (dogfood install — `clud-bug-collaboration` already differs), and **`clud-bug-app/lib/baseline-skills/` (a STALE ~v0.6.x vendored copy)**. One reservoir source + downstream mirrors would kill this class of drift — clud-bug is the canonical exemplar of why the model is needed.
- **Per-repo policy layer:** `.clud-bug.json` carries `strictMode` + `strictSkills` (which skills' critical findings fail the merge gate) — a repo-local posture *on top of* placement (currently strictMode: true, strictSkills: []). The census map is about *where a skill lives*; this is about *how hard it bites* per repo — worth a column if the reservoir ever models enforcement.
